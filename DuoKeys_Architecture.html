Technical review & developer handoff — v2

A piano tutor for two, rebuilt around the clock

The DuoKeys brief is a strong product idea with one fatal platform assumption and one missing subsystem. This document fixes both, then lays out the functional and technical architecture in enough detail to start writing code.

Source DuoKeys_Project_Specification.html Verdict Proceed — with a platform change Date 2 Sep 2026

00 — VerdictWhat survives, what has to change

The product thinking is sound: two genuinely different learners on one instrument, a gamified loop for the child and an analytical loop for the adult, all driven by real key presses rather than taps on glass. Keep all of it. Three things need to change before any code is written.

The iPad cannot do Web MIDI. It never has.

Blocker

Safari does not implement the Web MIDI API on iOS or iPadOS in any version, and Apple requires every iOS browser to use WebKit — so Chrome and Firefox on the iPad inherit the same gap. The entire hardware path in the spec (iPad + USB-C + Web MIDI API) does not exist. This is not a polyfill problem; there is no JavaScript that can reach a USB MIDI device from Safari.

FixChange the device, or add a native shell. Section 02 lays out the four options with costs. Recommendation: run on any laptop or Android tablet for now, and put every MIDI call behind a MidiBackend port so the decision stays reversible.

There is no timing subsystem, and timing is the whole product

Blocker

Every feature in the brief — falling notes, wait mode, ±150 ms star ratings, A/B looping, duet evaluation — is a statement about when a key was pressed relative to when it should have been. But MIDI events arrive stamped in the performance.now() domain, audio is scheduled in the AudioContext.currentTime domain, and the score lives in musical ticks. Three clocks, no mapping.

If this is improvised per-feature you get a system where the falling notes look right but the score says you were late, and nobody can tell whether the bug is in the game or in the player.

FixOne MasterClock owned by the core, plus a per-device latency calibration wizard. Section 05.

The hardest component gets one line

Major gap

"Parsing note-on events against target audio schedules" is the score follower — the component that decides whether a performance matched a score. It has to handle chords played slightly spread, ornaments, repeated notes, wrong notes next to right ones, skipped notes, and a six-year-old who stops for four seconds mid-bar. It is roughly 40% of the engineering effort in this project and needs a specified algorithm, not a reference repo.

FixTwo explicit matching modes with defined tolerance maths and error taxonomy. Section 07.

The shape of the fixAll three problems point the same way: put the musical logic in a pure, platform-free core, and treat MIDI, audio, storage and rendering as replaceable adapters around it. That single decision downgrades the iPad question from a blocker to a configuration choice, makes the score follower unit-testable without hardware, and gives the clock one owner. The rest of this document is that architecture.

01 — Review findingsThe rest of the review

Ordered by how much rework they cause if discovered late. Everything not listed here — the stack choices, the two-persona split, the phase themes — I would keep as written.

Design gaps

The synthesiser will fight the piano

Gap

The digital piano already makes sound, instantly, in hardware. Layering a Tone.js sampler on top gives you every note twice, the second one 20–60 ms late. Tone.js is still needed — for the metronome, backing tracks, the muted hand in hands-separate practice, and rewards — but it must never double the piano's own voice by default.

FixShip an Audio source setting: piano (default, app plays only accompaniment), app (for headphone practice with Local Control off on the instrument), both (off by default, opt-in).

The sustain pedal is not mentioned anywhere

Gap

CC64 changes what a note-off means. With the pedal down a released key keeps sounding; a player who holds the pedal through a whole exercise produces a legitimate performance that a naive matcher scores as one giant held chord. It also produces "hung notes" in any visualiser that keys off audio rather than key state.

FixA PedalTracker stage in the MIDI pipeline that separates key released from note stopped sounding. Grade on key state; render decay on sound state. Section 06.

A fixed ±150 ms window is the wrong tolerance

Gap

At 60 BPM, 150 ms is 15% of a beat — generous. At 132 BPM it is a third of a beat, which will pass performances that are audibly wrong. Beginners practise slowly, so the window is loosest exactly where accuracy matters most for habit forming.

FixTempo-relative windows with an absolute floor: tolerance = max(floorMs, beatMs × fraction), three tiers rather than one pass/fail. Section 07.

Three tables will not hold this product

Gap

profiles, lessons, progress_logs has no room for the distinction between a piece, an arrangement of that piece at a difficulty level, and a two-bar segment of that arrangement — which is exactly what the micro-quest feature is built on. There is also nowhere to record a per-note result, so the practice dashboard can only ever show "you played it" rather than "your left hand rushes bar 5".

FixPiece → Arrangement → Section, plus an Attempt with an embedded per-note event array. Section 09.

Cloud-first is the wrong default for a device on a music stand

Gap

Two independent problems. First, practice happens wherever the piano is, which is often the worst Wi-Fi in the house; a spinner between "sit down" and "play" will kill the habit faster than any missing feature. Second, Supabase pauses free-tier projects after seven days without API traffic — go on holiday, come back, and the app is down until someone logs into a dashboard.

FixLocal-first. IndexedDB is the source of truth; Supabase becomes an optional, additive sync target. Content ships as static JSON with the app and needs no database at all.

Duet mode ignores how twin-piano actually works

Gap

Splitting at MIDI 55/56 gives the child the top three-and-a-half octaves and the parent the bottom four, each in the wrong register for normal repertoire. Real digital pianos solve this with a Duo/Twin mode that splits the keyboard and transposes each half so both players get their own middle C. Without transposition the child reads a treble part and plays it two octaves high.

FixModel the split as { splitPoint, lowerTranspose, upperTranspose }, default ±2 octaves, and detect whether the instrument's own Duo mode is already doing it — if so the app must not transpose twice.

The roadmap is horizontal, so nothing is playable until Phase 2

Gap

Infrastructure → kid → adult → shared means the first moment anyone can actually sit at the piano and use the thing is somewhere in the middle of the second phase, after the riskiest components have all been built on assumptions. For a project whose core risk is "does the timing feel right", that is the wrong order.

FixVertical slices. One hard-coded eight-bar piece playable end-to-end — MIDI in, notes falling, stars out, saved locally — before any content pipeline, auth or second module exists. Section 13.

Missing from the feature set entirely

  • Latency calibration wizard. Without it the ±150 ms judgement is measuring your Bluetooth stack, not the player. Non-negotiable; ~half a day of work.
  • Device picker and connection state. What the app does when the cable is unplugged mid-song, when two devices are present, when the browser denies permission.
  • Metronome and count-in. A timed mode with no count-in is unplayable — the first note is always wrong.
  • Screen Wake Lock and orientation lock. The screen going to sleep four bars in is the single most likely reason this gets abandoned.
  • Session shape for a six-year-old. A soft session length (8–12 minutes), a natural stopping point, and no failure states in the first weeks. Design the loop to end well, not to maximise time.
  • An on-screen fallback keyboard. Needed for development, for testing, and for the evening the cable is missing.

02 — The iPad decisionFour ways out, one recommendation

This is the only decision in the document that has to be made before Sprint 0 ends, because it determines what "run the app" means. All four options keep the same codebase; they differ in what sits between the browser and the cable.

OptionWhat it meansCostEffortRisk
A. Change the device
Recommended		 Run in desktop Chrome or Edge on any laptop, or Chrome on an Android tablet, propped on the music stand. Web MIDI works natively and has since 2015. £0 – £150 None — zero code change Lowest. Also the best dev experience: DevTools on the same machine as the piano.
B. Keep the iPad, add a native shell Wrap the same web app in Capacitor and write a small Swift plugin bridging CoreMIDI into the WebView, exposing a MidiBackend-shaped JS API. $99/yr 3–5 days of Swift + ongoing build/signing Medium. Breaks the "$0/mo, no app store" premise. Free provisioning re-signs every 7 days, which is worse than paying.
C. Keep the iPad, use a third-party MIDI browser Open the deployed URL inside an App Store browser that bundles its own CoreMIDI-to-Web-MIDI shim. ~£5 Hours High. No home-screen PWA, no wake lock control, no fullscreen guarantees, and you are betting the project on one small app staying maintained.
D. Listen through the microphone Drop MIDI; use getUserMedia and pitch detection. £0 Weeks Unacceptable. Polyphonic transcription is unsolved at this accuracy; no velocity, no pedal, no note-off. It would make the grading dishonest.

Take A, and build so that B stays cheap. The recommendation is not "abandon the iPad" so much as "do not let the hardest platform gate the first working version". If the iPad on the stand matters to the family experience — and it plausibly does — build the whole app against the port interface, get the product right on a laptop, and treat the Capacitor bridge as a two-file adapter you write later, once the thing is worth putting in front of a child every day.

Decided — 2 Sep 2026Option A. Development and daily practice both run in a desktop browser (Windows laptop, Chrome/Edge) for now. The iPad shell (Option B, ~1 week, needs a Mac to build — rented or cloud) stays a scoped later addition, contingent on keeping the port boundary clean per the note below.

03 — Functional architectureWhat the product does

One household, two profiles, no passwords

A six-year-old should never see a login screen, and a family piano app has no reason to hold an email address for a child. The model is a household that owns profiles. The household may optionally be linked to a single adult account for cloud backup; profile switching is a tap on an avatar in the top bar and touches no credentials at all. Everything a child produces stays on the device unless the adult opts into sync.

Profile shape

core/src/domain/profile.ts
// A profile is a set of preferences and a progress ledger, not an identity.
export interface Profile {
  id: ProfileId;
  displayName: string;              // "Mia", "Dad"
  mode: 'explorer' | 'student';      // drives UI density + reward loop, not age
  avatar: AvatarKey;

  keyboardRange: { low: MidiPitch; high: MidiPitch };   // 61-key safety
  handSpan: number;                 // white keys reachable; gates repertoire
  audioSource: 'piano' | 'app' | 'both';
  calibration: Calibration;         // per profile: headphones differ per person

  sessionTargetMinutes: number;     // soft, used for the wind-down prompt
  createdAt: IsoDate;
}

mode is deliberately not 'kid' | 'adult'. It describes the kind of practice loop a person wants, so a nine-year-old can graduate into student mode and an adult can drop into explorer mode for fun without the app calling them a child.

The activity model

Every screen where a person plays is one Activity. Activities differ in presentation and in which matcher mode they run, but they all take an ExerciseSpec and emit an Attempt. This is what stops the kid module and the adult module from becoming two apps in one repository.

export interface ExerciseSpec {
  id: ExerciseId;
  source: { arrangementId: ArrangementId; sectionId?: SectionId };
  matchMode: 'wait' | 'timed';         // section 07
  hands: 'left' | 'right' | 'both';
  tempoScale: number;                    // 0.3 – 1.0 of the notated tempo
  transpose: number;                     // semitones, for range-limited keyboards
  loop?: { fromMeasure: number; toMeasure: number; count: number | 'until-clean' };
  accompaniment: 'none' | 'metronome' | 'backing' | 'other-hand';
  passCriteria: PassCriteria;
}

  id: AttemptId; profileId: ProfileId; exerciseId: ExerciseId;
  startedAt: IsoDate; durationSec: number;
  grade: Grade;                          // section 07
  events: MatchResult[];                 // per-note, for the dashboard and replay
  contextHash: string;                   // tempo + hands + transpose, so grades compare like-for-like
}

Explorer mode — the child's loop

Note Ninja

Single note on a grand staff, play it, next. The engine is a weighted sampler over a note pool, not a random one: notes the player has recently missed come back sooner. Store per-pitch ease factors and use a simplified Leitner schedule — the same machinery later drives interval and chord drills for the adult.

Replace the 5-second timer with a response-time band: under 2 s is a streak, 2–6 s is correct, over 6 s reveals a hint. Timers that fail a six-year-old teach them that reading music is frightening.

Falling notes + Wait Mode

Bars descend toward a hit line drawn directly above an on-screen keybed, so the mapping from screen to hands is spatial and needs no reading. Wait mode is the default and, in practice, the only mode a beginner should use for the first months: the stream freezes at the hit line until the correct keys are down.

Wait mode is not a pause of the transport — it is a different matcher (section 07). Treating it as "timed mode with pauses" causes the tempo-map drift bug that plagues most implementations.

Micro-quests

A piece is auto-segmented into 1–2 bar Sections at ingest. A quest is a Section plus a PassCriteria. Stars come from the three tolerance tiers rather than a single window, so improvement is visible before mastery is reached.

Unlock rule: clearing a Section unlocks the next and the "join" exercise covering both. Chaining backwards from the end of a phrase is how the piece gets learned rather than the first two bars getting learned twenty times.

Reward and stopping

Reward on effort as well as outcome: a "you fixed bar 3" event is more motivating and more honest than confetti for a lucky pass. The app should propose an ending — a favourite piece played once, then a summary the parent can see — at the session target, and never nag past it.

Student mode — the adult's loop

Score view

OSMD renders the MusicXML; the cursor is driven by the matcher, not by wall-clock playback. In practice mode the score waits for you, in performance mode it does not. Same component, different matcher — again the mode split earns its keep.

Per-note colouring on the rendered score (late / early / wrong / missed) after an attempt is the single highest-value feature for an adult re-learner and comes almost free once Attempt.events exists.

Practice suite

A/B loop by measure, hands-separate with the muted hand optionally played by Tone.js, tempo 30–100%. Add auto-ramp: on a clean pass, raise tempo 5% and repeat; on a failed pass, drop back one step. That one behaviour turns a set of controls into an actual practice method and is maybe thirty lines on top of the loop.

Technical drills

Hanon 1–20 is public domain and small enough to author directly as JSON rather than parse. Grade these on evenness — the standard deviation of inter-onset intervals and of velocity — rather than accuracy, because the notes are trivially correct and the whole point is the consistency.

Generated sight-reading

A constrained generator, not a random one: pick a key, a range, a rhythm vocabulary and an interval budget, then emit four bars that never repeat the previous exercise's opening. Seed it so a good exercise can be replayed or shared, and never generate something unplayable by the profile's hand span.

Duet mode

One instrument, two players, one score, two evaluation zones. The mechanics that matter:

  • Split with transposition. { splitPoint: 60, lowerTranspose: +12, upperTranspose: -12 } by default, so both players have a middle C. Ask at setup whether the piano's own Duo mode is engaged; if it is, the app transposes by zero and lets the hardware do it.
  • Two matchers, one transport. Each zone runs its own matcher against its own part, sharing the clock. Grades are reported separately — a child should never lose a star because the parent rushed.
  • Asymmetric difficulty. The primo part is five notes in one hand position; the secondo carries the harmony and the pulse. Model this as two Tracks in one Arrangement with a role field, so the same piece can be practised alone by either player.
  • Grace, not gates. If one player stops, wait mode should follow the player who is still going for a bar before pausing. Nothing kills a shared moment faster than a hard stop.

05 — The clockThree time domains, one timeline

The most important two hundred lines in the project. Get this right and every timing feature becomes straightforward; get it wrong and you will chase phantom bugs in the renderer, the matcher and the audio scheduler for months.

DomainUnitProduced byUsed for
WallMillisperformance.now() — Web MIDI timeStamp, rAFNothing. Converted on entry.
AudioSecondsAudioContext.currentTimeThe master. All matching, scheduling and rendering.
MusicalTicksThe score, at 480 PPQNotation, loops, tempo scaling. Mapped to audio via the tempo map.

The audio clock is the master because it is the only one guaranteed monotonic, drift-free relative to actual sound output, and shared with the scheduler. performance.now() can be throttled in background tabs and is not locked to the audio hardware; rAF timestamps are frame-quantised. Convert once, at the boundary, and never let a wall-clock number past the adapter.

core/src/clock/masterClock.ts
export type Millis  = number;   // performance.now() domain
export type Seconds = number;   // AudioContext.currentTime domain — canonical
export type Ticks   = number;   // musical, PPQ = 480

export interface MasterClock {
  now(): Seconds;
  fromWall(t: Millis): Seconds;    // MIDI timeStamp → canonical, latency-corrected
  readonly inputLatency: Seconds;
  dispose(): void;
}

export function createMasterClock(
  ctx: AudioContext,
  cal: Calibration,
): MasterClock {
  // offset maps the wall clock onto the audio clock. Both advance at ~1s/s but
  // they are not locked, so we re-estimate and let an EMA absorb the drift
  // while rejecting the jitter of any single sample.
  let offset = ctx.currentTime - performance.now() / 1000;
  const ALPHA = 0.02;

  const resync = () => {
    const sample = ctx.currentTime - performance.now() / 1000;
    offset += ALPHA * (sample - offset);
  };
  const timer = setInterval(resync, 1000);

  return {
    now: () => ctx.currentTime,
    fromWall: (t) => t / 1000 + offset - cal.inputLatency,
    inputLatency: cal.inputLatency,
    dispose: () => clearInterval(timer),
  };
}

Calibration — why it is not optional

Between the key going down and the app knowing about it sit the instrument's own scan rate, the USB stack, the browser's MIDI thread and the event loop. Between the app deciding to make a sound and the sound existing sit the audio graph and the output buffer. Neither is knowable in advance, and both vary by tens of milliseconds across devices. Judging a performance to ±50 ms without measuring them is judging the hardware.

core/src/clock/calibration.ts
export interface Calibration {
  inputLatency: Seconds;    // key down → event received
  outputLatency: Seconds;   // schedule → audible
  visualLead: Seconds;      // how far ahead to draw, = outputLatency + display lag
  measuredAt: IsoDate;
  method: 'tap' | 'default';
}

/**
 * Wizard: play a click on the beat for 16 beats; ask the player to play any
 * key exactly with it. Discard the first 4 (entrainment), take the median of
 * the signed offsets — median, not mean, because one distracted late tap
 * would drag an average by 20ms and there is no second chance to notice.
 */
export function estimateInputLatency(
  clickTimes: Seconds[],
  keyTimes: Seconds[],
): Seconds {
  const deltas = keyTimes
    .map((k) => k - nearest(clickTimes, k))
    .filter((d) => Math.abs(d) < 0.25);        // reject non-attempts
  return median(deltas.slice(4));
}

// AudioContext exposes its own estimate; use it as the starting point and
// as a sanity bound on what the wizard is allowed to return.
export function baselineOutputLatency(ctx: AudioContext): Seconds {
  return (ctx.outputLatency ?? 0) + (ctx.baseLatency ?? 0);
}

Run the wizard once per profile per audio route, store it on the profile, and re-prompt if the output device changes. Ninety seconds of setup buys every grade in the app its credibility.

Tempo mapping

Ticks convert to seconds through a piecewise-linear tempo map, scaled by the exercise's tempoScale. Keep the map immutable per attempt: changing tempo mid-attempt invalidates the grade and should end the attempt, not silently rescale it.

core/src/score/tempoMap.ts
export interface TempoEvent { atTicks: Ticks; bpm: number; }

export class TempoMap {
  constructor(private events: TempoEvent[], private ppq = 480) {}

  /** Musical position → seconds from the start of the piece. */
  toSeconds(ticks: Ticks, scale = 1): Seconds {
    let sec = 0, cursor = 0, bpm = this.events[0].bpm;
    for (const ev of this.events) {
      if (ev.atTicks >= ticks) break;
      sec += ((ev.atTicks - cursor) / this.ppq) * (60 / (bpm * scale));
      cursor = ev.atTicks; bpm = ev.bpm;
    }
    return sec + ((ticks - cursor) / this.ppq) * (60 / (bpm * scale));
  }
}

06 — MIDI pipelineFrom raw bytes to musical intent

Four stages, each a pure function of the previous one. Everything downstream — matcher, renderer, recorder — consumes the same PerformanceEvent stream, which is why the virtual keyboard and the fixture replayer are indistinguishable from a real piano to the rest of the app.

core/src/midi/ — the stream
//  raw bytes ─▶ decode ─▶ pedalTracker ─▶ noteStream ─▶ PerformanceEvent

export type PerformanceEvent =
  | { kind: 'noteOn';  pitch: MidiPitch; velocity: number; at: Seconds }
  | { kind: 'noteOff'; pitch: MidiPitch; at: Seconds; stillSounding: boolean }
  | { kind: 'pedal';   pedal: Pedal; value: number; down: boolean; at: Seconds }
  | { kind: 'sounded'; pitch: MidiPitch; at: Seconds };  // released by pedal lift

export function decode(data: Uint8Array, at: Seconds): RawEvent | null {
  const status = data[0] & 0xf0;
  switch (status) {
    case 0x90: return data[2] === 0
      ? { type: 'off', pitch: data[1], at }        // note-on velocity 0 IS a note-off
      : { type: 'on', pitch: data[1], velocity: data[2] / 127, at };
    case 0x80: return { type: 'off', pitch: data[1], at };
    case 0xb0: return { type: 'cc', cc: data[1], value: data[2], at };
    default:   return null;   // aftertouch, bend, clock — ignored, not an error
  }
}

The three bugs everyone writes1. Treating note-on with velocity 0 as a note-on — many instruments send this instead of note-off, and you get permanently held notes. 2. Assuming channel 1 — pianos in Duo mode often send the two halves on different channels, which you can actually exploit for duet mode. 3. Assuming events arrive in timestamp order — under load they do not, so buffer briefly and sort rather than trusting arrival order.

The pedal tracker

Its whole job is to keep two facts apart: the key is up (a fact about the player, which is what gets graded) and the note has stopped sounding (a fact about the instrument, which is what gets rendered).

core/src/midi/pedalTracker.ts
export class PedalTracker {
  private sustainDown = false;
  private heldByPedal = new Set<MidiPitch>();

  process(ev: RawEvent, emit: (e: PerformanceEvent) => void): void {
    if (ev.type === 'cc' && ev.cc === 64) {
      const down = ev.value >= 64;                // half-pedal: treat >=64 as down
      if (this.sustainDown && !down) {
        // lift: everything the pedal was holding stops sounding now
        for (const p of this.heldByPedal) emit({ kind: 'sounded', pitch: p, at: ev.at });
        this.heldByPedal.clear();
      }
      this.sustainDown = down;
      return emit({ kind: 'pedal', pedal: 'sustain', value: ev.value, down, at: ev.at });
    }

    if (ev.type === 'off') {
      // The KEY is up regardless of the pedal. That is what the matcher needs.
      if (this.sustainDown) this.heldByPedal.add(ev.pitch);
      return emit({ kind: 'noteOff', pitch: ev.pitch, at: ev.at,
                     stillSounding: this.sustainDown });
    }

    if (ev.type === 'on') {
      this.heldByPedal.delete(ev.pitch);           // re-struck
      return emit({ kind: 'noteOn', pitch: ev.pitch, velocity: ev.velocity, at: ev.at });
    }
  }
}

Connection lifecycle

Hardware disappears. The UI needs four explicit states, and an activity in progress must survive a brief disconnection rather than losing the attempt:

  • unsupported — the backend reports isAvailable() === false. Show the platform explanation and offer the on-screen keyboard, do not show a broken connect button.
  • needs-permission — requestMIDIAccess not yet granted. Must be triggered by a user gesture; note that Chrome's permission prompt does not appear on insecure origins, so local development needs HTTPS or localhost.
  • no-device / connected — with a live device picker, because a laptop may see the piano, a virtual port and an audio interface at once.
  • lost — device removed mid-attempt. Pause, hold the attempt open for 30 s, reconnect silently if the same device ID returns.

07 — Matcher & gradingDeciding whether that was right

Two matchers, one interface. Wait mode asks "are the right keys down?" and ignores time entirely. Timed mode asks "was each key down close enough to when it should have been?" Conflating them is the single most common way these apps go wrong.

core/src/match/types.ts
export interface ExpectedNote {
  id: NoteId;
  pitch: MidiPitch;
  at: Seconds;              // resolved through the tempo map at attempt start
  durationSec: Seconds;
  groupId: GroupId;        // notes sharing a group are one chord / one decision
  hand: 'left' | 'right';
  measure: number;
}

export type MatchResult =
  | { kind: 'hit';   noteId: NoteId; deltaSec: number; velocity: number; tier: Tier }
  | { kind: 'miss';  noteId: NoteId }
  | { kind: 'extra'; pitch: MidiPitch; at: Seconds; why: ExtraKind };

export type Tier = 'perfect' | 'good' | 'ok';
export type ExtraKind =
  | 'neighbour'   // within 2 semitones of an expected pitch — a slip
  | 'octave'      // right pitch class, wrong octave — a reading error
  | 'repeat'      // re-striking a note just played — hesitation, forgive it
  | 'foreign';    // unrelated — lost their place

export interface Matcher {
  feed(ev: PerformanceEvent): MatchResult[];
  tick(now: Seconds): MatchResult[];   // emits misses as their windows expire
  readonly cursor: GroupId | null;     // drives the OSMD cursor and the wait line
  readonly results: readonly MatchResult[];
}

Tolerance: relative to the beat, floored in milliseconds

Replaces the spec's flat ±150 ms. A fraction of a beat keeps the judgement musically meaningful across tempi; the floor stops it becoming unachievably strict at slow tempi, where it would otherwise be measuring the calibration error rather than the player.

core/src/match/tolerance.ts
const FRACTION = { perfect: 0.08, good: 0.16, ok: 0.32 };   // of one beat
const FLOOR_MS = { perfect: 45,   good: 90,   ok: 160  };   // absolute, ms

export function toleranceSec(bpm: number, tier: Tier): Seconds {
  const beatMs = 60_000 / bpm;
  return Math.max(FLOOR_MS[tier], beatMs * FRACTION[tier]) / 1000;
}

// At 60 BPM  → perfect 80ms  · good 160ms · ok 320ms
// At 120 BPM → perfect 45ms  · good 90ms  · ok 160ms   (floors bind)
// Chord spread is separate and generous: notes of one group played within
// CHORD_WINDOW count as simultaneous. Beginners roll chords; that is fine.
export const CHORD_WINDOW: Seconds = 0.09;

Wait mode — the child's matcher

No clock. The matcher holds a cursor on one group and advances when the set of currently-depressed keys contains every pitch in that group. Extra keys produce gentle feedback but never advance or fail. There is no way to lose.

core/src/match/waitMatcher.ts
export function createWaitMatcher(groups: NoteGroup[]): Matcher {
  let index = 0;
  const down = new Set<MidiPitch>();
  const results: MatchResult[] = [];

  function feed(ev: PerformanceEvent): MatchResult[] {
    if (ev.kind === 'noteOff') { down.delete(ev.pitch); return []; }
    if (ev.kind !== 'noteOn') return [];
    down.add(ev.pitch);

    const group = groups[index];
    if (!group) return [];
    const out: MatchResult[] = [];

    const satisfied = group.pitches.every((p) => down.has(p));
    if (satisfied) {
      for (const n of group.notes) {
        out.push({ kind: 'hit', noteId: n.id, deltaSec: 0, velocity: ev.velocity, tier: 'perfect' });
      }
      index++;
      // Do NOT clear `down`: legato means the next group may share held keys.
    } else if (!group.pitches.includes(ev.pitch)) {
      out.push({ kind: 'extra', pitch: ev.pitch, at: ev.at, why: classify(ev.pitch, group) });
    }
    results.push(...out);
    return out;
  }

  return { feed, tick: () => [], get cursor() { return groups[index]?.id ?? null; }, results };
}

Timed mode — greedy nearest-match under a monotonic constraint

Each incoming note is matched to the nearest unmatched expected note of the same pitch inside the widest window. "Nearest" rather than "first" matters for repeated notes; the monotonic constraint — never match backwards past an already-matched note — is what stops a hesitant player's late note from stealing the next bar's slot and cascading.

core/src/match/timedMatcher.ts
export function createTimedMatcher(expected: ExpectedNote[], bpm: number): Matcher {
  const W = toleranceSec(bpm, 'ok');          // widest acceptance window
  const open = new Set(expected.map((e) => e.id));
  let lastMatchedAt = -Infinity;
  const results: MatchResult[] = [];

  function feed(ev: PerformanceEvent): MatchResult[] {
    if (ev.kind !== 'noteOn') return [];

    const candidates = expected.filter(
      (e) => open.has(e.id)
          && e.pitch === ev.pitch
          && Math.abs(e.at - ev.at) <= W
          && e.at >= lastMatchedAt - CHORD_WINDOW,   // monotonic, chord-tolerant
    );

    if (candidates.length === 0) {
      const r: MatchResult = { kind: 'extra', pitch: ev.pitch, at: ev.at,
                                why: classifyAgainst(ev, expected, ev.at, W) };
      results.push(r); return [r];
    }

    const best = candidates.reduce((a, b) =>
      Math.abs(a.at - ev.at) <= Math.abs(b.at - ev.at) ? a : b);
    const delta = ev.at - best.at;

    open.delete(best.id);
    lastMatchedAt = Math.max(lastMatchedAt, best.at);
    const r: MatchResult = { kind: 'hit', noteId: best.id, deltaSec: delta,
                              velocity: ev.velocity, tier: tierFor(Math.abs(delta), bpm) };
    results.push(r); return [r];
  }

  // A note whose window has fully passed is a miss. Emitted from the render
  // loop so feedback appears at the moment it is musically true, not at the end.
  function tick(now: Seconds): MatchResult[] {
    const out: MatchResult[] = [];
    for (const e of expected) {
      if (open.has(e.id) && now > e.at + W) {
        open.delete(e.id);
        out.push({ kind: 'miss', noteId: e.id });
      }
    }
    results.push(...out);
    return out;
  }

  return { feed, tick, get cursor() { return currentGroup(expected, open); }, results };
}

Grading

One Grade per attempt, computed from the result list. Keeping grading separate from matching means you can re-grade a stored attempt under new criteria without re-recording it — useful when you inevitably tune the thresholds.

core/src/grade/grade.ts
export interface Grade {
  accuracy: number;       // hits / (hits + misses + penalised extras)
  timingRmsMs: number;    // root-mean-square of |delta| over hits
  rushDragMs: number;    // SIGNED mean delta — the actionable number
  evenness: number;       // 1 - normalised stddev of inter-onset intervals
  dynamics: number;       // velocity spread; flags "hammering everything"
  stars: 0 | 1 | 2 | 3;
  worstMeasures: number[];// bottom 3 by local accuracy → "practise bar 5"
}

// 'repeat' extras are hesitation, not error, and are excluded from accuracy.
// This one exemption is the difference between a scorer that feels fair
// and one a six-year-old learns to resent.
const PENALISED: ExtraKind[] = ['neighbour', 'octave', 'foreign'];

export function starsFor(g: Omit<Grade, 'stars'>, c: PassCriteria): 0|1|2|3 {
  if (g.accuracy < c.minAccuracy) return 0;
  if (g.accuracy >= 0.98 && g.timingRmsMs <= c.rmsPerfectMs) return 3;
  if (g.accuracy >= 0.90 && g.timingRmsMs <= c.rmsGoodMs)    return 2;
  return 1;
}

Report rush/drag, not just RMSRMS timing error tells a player they were inconsistent. Signed mean error tells them they rush — which is a thing they can actually fix, and which almost every returning adult does in exactly the same places. Surfacing rushDragMs per hand and per measure is a genuinely useful feature that costs one extra accumulator.

08 — RenderersCanvas for the game, OSMD for the score

Falling notes

Position is a pure function of time, never an accumulator — no y += velocity * dt, which drifts against the audio clock within seconds and is why so many rhythm games feel subtly wrong.

ui/src/canvas/fallingNotes.ts
// One frame. Read the clock once; derive everything from it.
function drawFrame(ctx2d: CanvasRenderingContext2D, s: RenderState) {
  const t = s.clock.now() + s.cal.visualLead;   // draw the future we will hear
  const pxPerSec = s.hitLineY / s.leadSeconds;  // leadSeconds ≈ 2.5s for beginners

  ctx2d.clearRect(0, 0, s.w, s.h);

  for (const n of s.notes) {
    if (n.at > t + s.leadSeconds || n.at + n.dur < t - 0.4) continue;  // cull
    const y = s.hitLineY - (n.at - t) * pxPerSec;
    const { x, w } = s.layout.rect(n.pitch);      // pitch → keybed geometry
    ctx2d.fillStyle = s.palette[n.hand][n.state];  // pending | hit | missed
    roundRect(ctx2d, x, y - n.dur * pxPerSec, w, n.dur * pxPerSec, 4);
  }
}

// Two stacked canvases: the keybed and gridlines are static and drawn once
// on the lower one; only the note layer is cleared and repainted per frame.
// On a 4K display that is the difference between 60fps and 35fps.

Layout

The pitch→x mapping is worth isolating and testing: white keys tile uniformly, black keys are inset and overlap, and the pattern repeats every octave with the 2–3 grouping. Derive it once from the profile's keyboardRange so a 61-key instrument renders a 61-key keybed rather than a scaled-down 88.

Score view

  • Instantiate OSMD once per arrangement and re-use it; construction and layout are expensive and re-rendering on every state change will drop frames.
  • Drive the cursor from matcher.cursor, not from a timer. One binding, both modes.
  • Colour notes from Attempt.events after the attempt, using OSMD's note-to-SVG mapping. This is the adult module's payoff feature.
  • Render at a fixed zoom and scroll by transform, not by re-layout — OSMD re-layout on scroll is the usual cause of stutter.
  • Pre-render off-thread where possible. Sections are known ahead of time; laying out the next page during the current one keeps page turns invisible.

10 — Content pipelineFrom MusicXML to playable quests

A build-time script, not a runtime import. Parsing MusicXML in the browser on a music stand is slow, failure-prone and unnecessary when the catalogue changes once a month.

content/build/ingest.ts — the stages

2. parse      → notes, tempo map, key/time signatures, part→hand mapping
3. normalise  → 480 PPQ, absolute ticks, ties merged, grace notes resolved
4. group      → assign groupId: notes within 30 ticks are one decision
5. segment    → Sections on phrase boundaries, falling back to 2 bars
6. analyse    → range, hand span, difficulty 1–5, tags

Difficulty scoring

A transparent heuristic beats a magic number, because you will need to argue with it. Score each arrangement on five axes and take a weighted sum: pitch range, hand-position changes (how often the thumb must move), rhythmic vocabulary (shortest subdivision and presence of ties across beats), hand independence (how often the hands play different rhythms), and accidental density. Publish the sub-scores in the JSON so a piece that lands wrong can be diagnosed rather than hand-overridden.

Sequence to a known method, don't invent oneNo lessons are booked yet, but the child module should still track the beginner sequence mainstream method books (Faber Piano Adventures, Alfred, Bastien) largely agree on, not a bespoke order: 1 pre-staff five-finger position centred on middle C, notes read by direction and interval rather than named pitch; 2 the same five-finger shape moved to a couple of neighbouring positions (D, G); 3 landmark-note reading — middle C, bass F, treble G as anchors, everything else read by distance from them; 4 full grand-staff reading once those anchors are solid. Map difficulty 1–5 onto these four stages now, so that if a specific method book is chosen later, re-keying the ladder to its exact page order is a lookup-table change, not a content rewrite.

11 — TestingHow you test a piano app with no piano

This is the payoff for the pure core. CI has no MIDI device, no audio hardware and no six-year-old, and needs none of them.

Unit — the core, exhaustively

The matcher, tolerance maths, tempo map, pedal tracker and grader are pure functions over event arrays. Test them the way you would test a parser: many small cases, no mocks, no framework beyond Vitest.

Property tests earn their place here. A perfect performance always grades 3 stars at every tempo. Adding a constant offset to every note changes rushDrag but not RMS. No permutation of chord notes within CHORD_WINDOW changes the grade.

Golden fixtures — the real safety net

Record actual performances through midi-replay as JSON: one clean, one rushed, one with two wrong notes, one with heavy pedal, one that stops halfway, one from the child. Assert the exact grade. When you tune a threshold, the diff across the fixture set shows you precisely who it helps and who it hurts.

Twenty minutes of recording buys you the confidence to change the matcher for the next two years.

Integration — the runtime wiring

Compose the real core with midi-replay, a stub AudioBackend and fake-indexeddb. Run a whole attempt headlessly and assert the stored Attempt. Catches the composition-root bugs unit tests structurally cannot.

End-to-end — Playwright

Expose window.__duokeys.midi.emit(bytes, t) in test builds so Playwright drives the virtual backend. Cover: connect flow, permission denial, device-lost-mid-song, profile switch, quest completion, offline reload.

Screenshot-test the canvas at fixed clock values by injecting a deterministic clock — a frozen now() makes the renderer as testable as any component.

What you still have to test by hand

Perceived latency, whether the falling-note lead time feels right, whether wait mode is forgiving enough, and whether a six-year-old wants to come back tomorrow. Nothing automates these. Budget a real session at the piano at the end of every sprint — it is the only test that measures the actual product.

Accessibility and child-appropriateness

  • Explorer mode stays icon-and-audio-led even though the child reads. The confirmed reader can take short text labels (§12) as a bonus channel, but icons, colour, animation and spoken prompts still carry the interface — a six-year-old's reading is far behind their listening, and it keeps the mode usable by a younger sibling or a bad day.
  • Do not encode meaning in colour alone — note state needs shape or position too. Colour-blindness in the family is likelier than you would guess, and the hand colours are the first thing to break.
  • Touch targets 44 px minimum, and nothing important within a thumb's reach of the screen edge where a small hand will rest it.
  • Respect prefers-reduced-motion — the falling notes themselves stay, the celebratory particle effects do not.
  • No dark patterns. No streak-loss anxiety, no timed pressure in the first weeks, no artificial scarcity. This is a six-year-old's relationship with music.

Privacy

Local-first makes this nearly free, and it is worth keeping deliberately: no third-party analytics, no audio ever leaving the device, no child email address, first names only. If sync is enabled, the adult's account is the only credential in the system. Should the app ever go beyond the family, that posture is also what keeps COPPA and GDPR-K from becoming a project of their own.

Platform housekeeping

  • Screen Wake Lock acquired on entering an activity, released on leaving. Re-acquire on visibility change — the lock is dropped when the tab is hidden.
  • AudioContext resume on user gesture, and a visible "tap to start" if it is suspended. Autoplay policy will otherwise silently kill the metronome.
  • Secure context. Web MIDI needs HTTPS or localhost. Point a dev tunnel at the machine or run the dev server on the same device as the piano.
  • Service worker caching the app shell and all content JSON, with a version-bumped cache and an explicit "new lessons available" prompt rather than a silent swap mid-song.
  • Kiosk the device. Guided Access on iPad, screen pinning on Android. The single most effective feature for a six-year-old's focus is not being able to leave the app.
